## 三、分析结论（基于自动化基准数据 data1.log）

### 3.1 功耗模式影响

| 对比项 | 15W | 25W | 提升幅度 |
|-------|-----|-----|---------|
| 纯文本 decode（纯文本模型） | 15.3 tok/s | 23.8 tok/s | **+56%** |
| 纯文本 decode（+mmproj） | 15.3 tok/s | 23.8 tok/s | **+56%** |
| 纯文本 prefill（纯文本模型） | 231.3 t/s | 373.6 t/s | **+62%** |
| 纯文本 prefill（+mmproj） | 231.6 t/s | 369.5 t/s | **+60%** |
| 稳态 TTFT | 115ms | 72-73ms | **-37%** |
| CLI 纯文本 prefill | 151.1 t/s | 291.7 t/s | **+93%** |

**结论**：功耗模式是影响性能的最大因素。25W（MAXN）下 GPU 频率解锁，prefill 和 decode 均提升 50% 以上，TTFT 缩短约 1/3。**对性能敏感的应用务必锁定 25W/最高功耗模式**。

### 3.2 mmproj（视觉组件）开销

| 对比项（25W, 纯文本任务） | 纯文本模型 | +mmproj | 变化 |
|-------|-----------|---------|------|
| prefill 速度 | 373.6 t/s | 369.5 t/s | 持平（-1%） |
| decode 速度 | 23.8 tok/s | 23.8 tok/s | 持平 |
| 稳态 TTFT | 73ms | 72ms | 持平 |
| 常驻内存（基线） | 5389MB | 7296MB | **+1907MB** |

**结论**：加载 mmproj 后常驻内存增加约 **1.9GB**，但对纯文本推理性能（prefill/decode/TTFT）**完全无影响**——视觉编码器只在处理图片时才被调用。8GB 设备上多模态常驻 ~7.3GB 已接近上限，需注意控制上下文和并发。

### 3.3 图片输入开销（真实图片 prefill）

图文测试第 1 轮（455 tok 真实图片编码, 未命中缓存）与纯文本稳态轮对比：

| 指标 | 纯文本 15W | 图文 15W | 纯文本 25W | 图文 25W |
|-------|-----------|---------|-----------|---------|
| Prefill 耗时 | 115ms | **2525ms**（22 倍） | 72ms | **1694ms**（24 倍） |
| Prefill 速度 | 231.3 t/s | 180.2 t/s | 372.0 t/s | 268.6 t/s |
| TTFT | 115ms | **2525ms** | 72ms | **1694ms** |
| Decode 速度 | 15.3 tok/s | 15.2 tok/s | 23.9 tok/s | 23.5 tok/s |

**结论**：
- 图片输入的开销集中在 **prefill 阶段**：455 个输入 token 中约 428 个是图片 token，视觉编码耗时是纯文本的 22~24 倍
- 图片 prefill 速度（180~269 t/s）低于纯文本（231~372 t/s），因为 mmproj 视觉编码器与文本 prefill 共用此阶段
- **decode 速度完全不受图片影响**——生成阶段不涉及视觉编码（15.2≈15.3 / 23.5≈23.9）
- **图片缓存效应显著**：同图第 2 次请求 TTFT 从 1694~2525ms 降至 73~116ms（约 22 倍加速），重复图片场景（如视频抽帧、监控）可大幅受益

### 3.4 内存特征

- **推理内存增量极小**（+9 ~ +44MB）：模型权重常驻内存，单次推理的额外开销主要是 KV cache 增长
- **多轮测试内存缓慢爬升**（15W +mmproj 组：6951→7323MB）：每轮唯一提问导致 KV cache 持续增长，实况长期运行需关注上下文回收
- **图文任务内存曲线先升后降**：图片编码期间的临时内存在生成阶段被释放
- **8GB 上限约束**：多模态模式常驻 ~7.1-7.3GB，剩余空间有限，建议 `--ctx-size ≤ 3072`

### 3.5 冷启动效应

每组第 1 轮（prompt_n=50, 含系统消息重新编码）比稳态轮（prompt_n=27）慢：
- prefill 耗时约为稳态的 2 倍（228ms vs 115ms）
- TTFT 同样翻倍
- decode 速度不受影响

**结论**：评估真实用户体验时，首次请求延迟约为稳态的 2 倍（纯文本）；生产环境建议服务启动后先做一次预热请求。

```bash
# CLI 纯文本
./build/bin/llama-cli -m <model.gguf> -p "解释量子计算的基本原理" -n 512 --ctx-size 2048

# CLI 图文
./build/bin/llama-cli -m <model.gguf> --mmproj <mmproj.gguf> --image <img.jpg> -p "这张图片里有什么？" -n 256 --ctx-size 2048

# Server 内存峰值测试（tegrastats 采样）
python test_memory.py --prompt "解释量子计算"              # 纯文本
python test_memory.py --image ./test.jpg --resize 768      # 图文

# 自动化基准测试（唯一提问绕过缓存, 多轮取平均, 输出 Markdown 表格）
python bench_auto.py --rounds 5 --no-image                 # 纯文本 5 轮
python bench_auto.py --no-text --image ./test.jpg --resize 768   # 图文 3 轮
# 注: 测真实图片 prefill 时每组换不同图片（同图会命中服务器图片缓存）
```

### 指标口径说明

| 指标 | 说明 |
|------|------|
| Prefill 速度 | 输入 token 处理速度（含图片编码），TTFT 的主要构成 |
| Decode 速度 | 生成 token 速度，即日常说的"推理速度" |
| TTFT | 首 token 延迟 ≈ prefill 耗时 |
| 内存 | tegrastats 系统统一内存（CPU/GPU 共享），1 秒采样取峰值 |
| 文本缓存 | server 对重复文本命中 prompt cache（prompt_n 骤降）；bench_auto.py 用唯一编号绕过 |
| 图片缓存 | 同一张图片的视觉编码结果也会被缓存（图片 token 变 0），测真实图片 prefill 需每组换图 |
| 冷启动轮 | 每组第 1 轮含额外开销（prompt_n=50），稳态轮 prompt_n=27 |
