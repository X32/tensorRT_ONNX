# MLC-LLM 交叉编译实验报告

**实验日期**: 2026年8月14-15日  
**实验人员**: AI辅助部署团队  
**实验场景**: PC端交叉编译 Qwen2.5-1.5B/3B 模型至 Jetson Orin 8GB 设备运行

---

## 一、实验摘要

本实验验证了 MLC-LLM 在 Jetson Orin 8GB 设备上的 PC 端交叉编译部署方案。通过与设备端 JIT（Just-In-Time）编译方案对比，证实交叉编译方案在**保持零性能损失**的前提下，显著改善了**部署运维效率**和**系统稳定性**。

**核心结论**:
- ✅ 交叉编译产物与 JIT 版本吞吐性能持平（±3% 差异在噪声范围内）
- ✅ 3B 模型首次响应时间（TTFT）改善 44%（0.175s → 0.098s）
- ✅ 部署时间从 2分钟/设备降至秒级，支持完全离线部署
- ✅ 规避了 8GB 内存 JIT 编译 OOM 风险

---

## 二、实验目的

1. **验证可行性**: 确认 MLC-LLM 能否从 PC（x86_64）交叉编译至 Jetson Orin（ARM64 + sm_87 GPU）
2. **性能对比**: 量化交叉编译方案与 JIT 方案在推理速度、资源占用上的差异
3. **运维评估**: 对比两种方案在部署复杂度、时间成本、稳定性方面的差异
4. **文档沉淀**: 建立可复用的标准操作流程（SOP）和问题排查手册

## 五、实验过程与问题解决

### 5.1 交叉编译全流程踩坑记录

本实验历时两天，从零构建镜像到成功运行共计遇到 **8 个关键坑位**，按优先级排序：

#### 坑 ① - `import tvm` 失败：pytest 依赖缺失
- **现象**: 镜像构建验证层 `python -c "import tvm"` 崩溃
- **根因**: 新一代 TVM 将 pytest 写入顶层导入链（`tvm.rpc.testing` → `tvm_ffi.testing`）
- **修复**: Dockerfile 增加独立层 `RUN uv pip install pytest`
- **方法论**: 上游依赖变化频繁，验证命令需对着实际源码核对

#### 坑 ② - `tvm.support.libinfo` API 消失
- **现象**: 验证 LLVM 支持时报 `AttributeError: module 'tvm.support' has no attribute 'libinfo'`
- **根因**: 新版 TVM 已移除此 API，旧文档/博客中的检查方法全部过时
- **修复**: 改用功能探测：
  ```python
  python -c "import tvm; tvm.get_global_func('target.build.llvm'); print('OK')"
  ```
  该函数仅在 `#ifdef TVM_LLVM_VERSION` 内注册，存在即代表 LLVM 真正编入 libtvm.so

#### 坑 ③ - 容器运行时找不到插件库
- **现象**: 构建验证通过，但 `docker run` 起的容器报 `OSError: libfpA_intB_gemm.so: cannot open shared object file`
- **根因**: 构建期的 `LD_LIBRARY_PATH` 只在当前 RUN 层生效，不会继承到运行时容器
- **修复**: 新增层固化到 ld 缓存：
  ```dockerfile
  RUN find /opt/mlc-llm /opt/venv -name '*.so' -printf '%h\n' | sort -u \
          > /etc/ld.so.conf.d/mlc-llm.conf \
      && ldconfig
  ```
- **关键细节**: **切勿将 CUDA stubs 目录加入 ld 缓存**，否则运行时真驱动会被顶掉

#### 坑 ④ - 【核心】ABI 不兼容：`undefined symbol: TVMFFIErrorSetRaisedFromCStrParts`
- **现象**: 交叉编译产物在 Jetson 上 `dlopen` 报符号缺失
- **诊断三步法**（通用方法）：
  1. Jetson 端 `nm -D libtvm.so \| grep <symbol>` → 确认符号确实不存在
  2. `find / -name 'libtvm_ffi*'` → 排除库路径问题
  3. 容器内 `git log -1` → 查明实际版本：
     - mlc-llm = `d2118b3`（2025-05-01 main）
     - TVM = `9c894f78`（旧代 FFI，无 tvm-ffi 子模块）
- **根因**: `dustynv/mlc:0.20.0-r36.4.0` 版本号具有误导性：
  - 容器构建自 mlc-llm main 快照，钉的是**旧一代 FFI 的 TVM**
  - GitHub v0.20.0 release tag 钉的是**新一代 tvm-ffi TVM**
  - 两代 TVM 的 C ABI 不兼容，导致 `.so` 加载失败
- **修复**: 放弃 `--branch v0.20.0`，改为钉 commit：
  ```dockerfile
  ARG MLC_COMMIT=d2118b3c9d56da6d1e66dfe2667f650020417010
  RUN git clone https://github.com/mlc-ai/mlc-llm /opt/mlc-llm \
      && cd /opt/mlc-llm \
      && git checkout ${MLC_COMMIT} \
      && git submodule update --init --recursive --depth 1
  ```
  同时调整：Python 3.13 → 3.10（旧代 TVM Cython 不支持 3.13）、删除 tvm-ffi 安装步骤

#### 坑 ⑤ - 官方 wheel 索引无 aarch64 包
- **结论**: `https://mlc.ai/wheels/` 全索引无 aarch64 包，Jetson 无法通过 pip 安装任何官方 MLC 运行时
- **影响**: dustynv 容器成为唯一现实选择 → 编译端必须迁就运行端（即坑④的修复方向）

#### 坑 ⑥ - 权重文件传输布局错误
- **现象**: scp 传输后 Jetson 上 `mlc-chat-config.json` 不存在，脚本回退去连 HF（网络不通卡死）
- **根因**: 传输了目录内容而非目录本身，30 个 `params_shard_*.bin` 被平铺在 `dist/` 下
- **修复**: 重新传输正确目录结构；`jetson-run.sh` 放宽库探测为 `find ~/work/mlc/dist -name '*sm87.so'`

#### 坑 ⑦ - 老源码的"裸构建依赖"四连
钉回 `d2118b3` 后，切回 cmake + setup.py 流程，连续踩中四个依赖缺失：

| 依赖 | 现象 | 原理 | 修复 |
|------|------|------|------|
| cmake/ninja | `cmake: not found` | 以前在 pip 隔离环境，镜像 PATH 没有 | `apt install cmake ninja-build` |
| setuptools | `No module named 'setuptools'` | CMake 裸调 setup.py，绕过 pip | `uv pip install setuptools cython` |
| Python.h | `fatal error: Python.h` | distutils 查找 `/usr/include/python3.10` | `apt install python3.10-dev` |
| Rust lint | `dangerous_implicit_autorefs` | 新版 rustc 把隐式引用定为 deny，但 CMake 用 `TOKENIZERS_CPP_RUSTFLAGS` 覆盖了 RUSTFLAGS | `sed` 按编译器建议改为显式引用 |

**方法论**: 
- 老一代源码（9c894f78/d2118b3）真正的打包入口在 `python/` 子目录，根目录的 `pyproject.toml` 仅用于代码风格配置
- 依赖安装层必须放在编译层**之前**且带自检（如 `ls Python.h`），在 25 分钟的 TVM 全量编译前拦住失败

#### 坑 ⑧ - 显存不足：temp_buffer 编译期烘焙
- **现象**: `.so` 加载成功（无符号错误），但引擎初始化报 `temporary buffer size (10771 MB)` 超出 8GB
- **根因链**:
  1. `gen_config` 未限参数时，Qwen2.5 默认 `prefill_chunk_size=8192`、`context_window_size=32768`
  2. 预填充函数按 8192 token 一次算 logits（151936 词表），单函数工作区 ~5.3GB
  3. 该工作区在**编译时**写入 `.so` 的 `ModelMetadata(memory_usage)`，运行时再 ×2 保险 → temp_buffer=10616MB
  4. **运行时无法修改**：改 `mlc-chat-config.json` 或 `--overrides` 均无效（库模式以 `.so` 元数据为准）
- **修复**: gen_config 加参数重新编译：
  ```bash
  --prefill-chunk-size 2048 --context-window-size 4096 --max-batch-size 1
  ```
  重编后 temp_buffer 降至 ~2.7GB
- **判定方法**: 启动日志中 `temp_buffer = XXXX` 纹丝不动，即说明这是编译期烘焙值

### 5.2 最终构建配置（可用版本）

| 组件 | 版本/提交 | 关键参数 |
|------|----------|---------|
| MLC-LLM 源码 | `main @ d2118b3` | 钉 commit，不用 v0.20.0 tag |
| TVM 子模块 | `relax @ 9c894f78` | 旧代 FFI，与 dustynv 容器同源 |
| Python | 3.10 | 旧代 TVM Cython 不支持 3.13 |
| 编译参数 | `--host aarch64-unknown-linux-gnu` <br> `--device '{"kind":"cuda","arch":"sm_87",...}` <br> `--opt "flashinfer=0;...;cudagraph=1;cutlass=1"` | sm_87 = Jetson Orin GPU 架构 |
| 配置参数 | `--prefill-chunk-size 2048` <br> `--context-window-size 4096` | 压低编译期工作区，适配 8GB 显存 |

### 5.3 标准操作流程（SOP）

#### PC 端 - 镜像构建与交叉编译

## 六、实验结果

### 6.1 生成性能对比

| 指标 | 模型 | JIT 版 | 交叉编译版 | 差异 |
|------|------|--------|-----------|------|
| **吞吐** | 1.5B | 60.05 tok/s | 59.42 tok/s | **-1.0%**（持平，噪声内） |
|  | 3B | 33.11 tok/s | 32.26 tok/s | **-2.6%**（持平，噪声内） |
| **首次响应时间（TTFT）** | 1.5B | 0.077s | 0.077s | 持平（均为热身后） |
|  | 3B | 0.175s | **0.098s** | **✅ 快 44%** |
| **GPU 利用率** | - | 96-99% @1013MHz | 98-99% @1013MHz | 同为算力瓶颈，非带宽限制 |

**数据来源**: 
- JIT 版: `DOC/log/run_step_20260814_19_25.log`
- 交叉编译版: `DOC/log/pc_compress_20260815_11_5.log` 及 `benchmark-result.txt`

**结论**: 
1. **吞吐零损失** - 两档模型差异均在 ±3% 噪声范围内，交叉编译产物与 JIT 内核同源符合理论预期
2. **3B TTFT 显著改善** - 从 0.175s 降至 0.098s，得益于编译期优化的 prefill 配置

### 6.2 资源占用对比

| 指标 | 模型 | JIT 版 | 交叉编译版 | 差异 |
|------|------|--------|-----------|------|
| **整机 RAM** | 1.5B | 4.44GB | 4.52GB | +0.08GB（可忽略） |
|  | 3B | 5.02GB | 5.25GB | +0.23GB（交叉版编译窗口 4096，JIT 版运行时压至 2048） |
| **功耗** | - | 20.2-21.4W | 19-21W | 持平 |
| **GPU 温度** | - | 56.8-60°C | 60-62°C | 持平（同水位） |

**结论**: RAM 代价可忽略，3B 多占的 0.23GB 源于配置窗口差异（4096 vs 2048），非架构开销。

### 6.3 运维差异对比（交叉编译核心价值）

| 维度 | JIT 版 | 交叉编译版 | 改善幅度 |
|------|--------|-----------|---------|
| **首次启动时间** | 设备端编译 ~2 分钟/模型，需挂 swap 防 OOM | 秒级加载，设备端零编译 | **✅ ~120x** |
| **编译发生地** | Jetson 8GB（风险点） | PC 31GB（无压力） | **✅ 规避 OOM 风险** |
| **部署复制** | 每台设备各自编译，结果受设备状态影响 | 产物即资产：`.so` + 权重 scp 即用，可版本管理 | **✅ 标准化可复制** |
| **网络依赖** | 首次需 HF 下载 + 编译 | **✅ 全离线可用** |
| **3B 适配** | 靠运行时 overrides 压参数 | gen_config 编译期定型，配置随产物走 | **✅ 配置一致性保证** |

**结论**: 运维收益是决定性的——从"每台设备现场编译 + 防 OOM + 依赖网络"变为"拷贝即部署"。

### 6.4 显存峰值实测

| 模型 | 权重大小 | 峰值显存占用 | 运行余量 | 优化手段 |
|------|----------|-------------|---------|---------|
| Qwen2.5-1.5B q4f16_1 | ~1.2GB | 2.5-3GB | ~5GB | prefill_chunk_size=2048 |
| Qwen2.5-3B q4f16_1 | ~2.2GB | 3.5-4GB | ~4GB | context_window_size=4096 |

**注意**: 8GB Orin 上同时只能跑一个引擎实例。测试前需 `docker ps` 清掉旧容器，挂着的旧 serve 会占 2-3GB 显存。

## 七、结论与建议

### 7.1 核心结论

1. **✅ 技术可行性验证**: PC 端交叉编译至 Jetson Orin 完全可行，产物与 JIT 版本性能持平
2. **✅ 运维收益显著**: 部署时间从分钟级降至秒级，支持完全离线，规避设备端编译 OOM 风险
3. **✅ 3B 模型可用**: 经编译期参数优化（prefill_chunk_size=2048），在 8GB 设备上稳定运行
4. **⚠️ 版本对齐关键**: 必须以 commit hash 对齐，不能仅依赖版本号（dustynv 容器 vs v0.20.0 tag 的教训）

### 7.2 推荐部署方案

**优先使用交叉编译方案**，适用于以下场景：
- ✅ 需要在多台 Jetson 设备上部署同一模型
- ✅ 网络受限环境（离线部署）
- ✅ 对部署时间敏感（秒级启动）
- ✅ 8GB 设备运行 3B 模型（规避 JIT OOM）

**JIT 方案适用场景**：
- 快速原型验证（单设备、模型频繁切换）
- 不稳定的开发环境（无需维护编译产物）

### 7.3 后续优化方向

1. **EAGLE 投机解码**: 可进一步提速 1.5-1.8x（需额外 136MB 显存，3B 模型需评估余量）
2. **量化探索**: `--quantize-embedding` 可节省 0.3-0.5GB，但需评估精度损失
3. **批处理优化**: 当前 `max_batch_size=1`，多并发场景可考虑调大（需重新编译）

### 7.4 关键方法论总结（可复用于其他项目）

1. **版本对齐要以二进制为准，不以版本号为准**
   - 对齐手段：两端 `git log -1` 对 commit；`.so` 加载失败先 `nm -D` 查符号归属
   
2. **fail-fast 验证必须覆盖真实运行路径**
   - 构建层内的临时环境变量（LD_LIBRARY_PATH）不会进镜像运行时
   - 验证判据应该是"容器 run 起来能跑"，而不只是"构建层内能跑"

3. **诊断三件套**
   - `nm -D <lib>.so \| grep <symbol>` —— 符号在不在，定 ABI 归属
   - 容器内 `git log -1` / `pip show` —— 实际版本考古
   - `find <dir> -name '*.so'` —— 库文件实际在哪

4. **修复要放进正确的层**
   - 加依赖放独立 RUN 层（不破坏编译缓存）
   - 运行时路径问题固化进镜像（ld.so.conf.d），不要指望运行命令里补环境变量

5. **上游 API 过时很快**
   - 网上教程的验证命令（如 `tvm.support.libinfo()`）对着钉住的 commit 源码核一遍再用
   - 用「功能探测」（get_global_func）替代「配置读取」更耐版本变化

6. **回退链要有日志**
   - 脚本「找不到 A 就去 B」的回退必须打印明确提示
   - 否则上游路径问题会被掩盖成下游网络问题
